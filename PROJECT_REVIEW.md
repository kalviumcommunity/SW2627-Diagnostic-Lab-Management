# LabTrack project review

Review date: 1 November 2026. Static review of application entry points, authentication, role workflows, data models, persistence, tests, Android configuration, CI, Docker, and product claims. These are source-backed findings; deployed Firebase rules, cloud settings, devices, printers, and production data were not inspected. Severity assumes use with real patient data. This is not a guarantee that every possible defect has been discovered.

## Critical: authentication and access

1. **Database rules permit everyone to read, modify, and delete everything.** `lab_track/firestore.rules:8` uses `if true` across all documents. If deployed, no authentication, ownership, branch isolation, or audit protection exists.
2. **Incorrect passwords can still log users in.** `auth/backend/repositories/auth_repository.dart:187` falls through from Firebase invalid-credential failures to a seed lookup without checking the password, then to `signInAsRole` even for an unknown email. Production and demo authentication share the same path.
3. **A universal OTP bypass exists.** The same repository, line 569, accepts `123456` independently of Firebase verification. Any code is accepted for a verification ID beginning with `demo-`.
4. **Privileged role entry is public.** `auth/frontend/screens/role_selection_screen.dart:46` exposes quick demo entry into roles, including administrator. `signInAsRole` returns a privileged identity without Firebase authentication or a build-time demo restriction.
5. **Users can choose privileged roles during registration.** Role selection is passed directly to email/Google account creation. No trusted staff provisioning or administrator approval establishes entitlement. Fetch failures or missing user profiles also fall back to the requested role.
6. **Patient identity is hardcoded in the patient provider.** `patient/frontend/providers/patient_provider.dart:29–38` initializes and refreshes `PT-84210`, irrespective of the authenticated patient. Other patients can see John's sample and reports, and their own bookings can disappear from the tracker on the next store update.
7. **Barcode tracking has no ownership check.** `patient/backend/services/patient_api_service.dart:96` searches the entire store by barcode and returns the sample regardless of patient identity. The UI offers example barcodes belonging to other people.
8. **Signing does not authenticate a pathologist.** `lab/frontend/widgets/pathologist_sign_dialog.dart:20` accepts a typed name; the store authorizes using a fixed `PATH-01` actor. There is no separate pathologist permission, signature proof, or binding to the logged-in signer. The patient UI nevertheless claims cryptographic validation.

## High: specimen and report integrity

9. **The main store bypasses the lifecycle state machine.** `data/services/central_data_store.dart:740–1135` assigns statuses directly. Rejected/completed samples can be accessioned or processed again, and reports can be signed without valid prior steps. The state machine is enforced only by a separate repository path.
10. **Two conflicting write paths run during collection.** `phlebotomist/backend/services/phlebotomist_service.dart:118` updates the central store to `inTransit`, then launches a repository transaction to `collected`. Depending on execution order, that transaction either conflicts with lifecycle validation or writes a different state. These futures are not awaited, so surrounding synchronous try/catch blocks do not reliably catch failures. Handover repeats this dual-write design.
11. **Barcode binding can associate one vial with two orders.** `confirmPhlebotomistCollection` appends the barcode to the selected order, but updates an existing sample without checking its order/patient ownership or rebinding those fields. The availability check allows an already-booked sample and is not atomic with collection.
12. **IDs are collision-prone.** Patient bookings use only the final six digits of a millisecond timestamp for orders and five for samples (`patient_api_service.dart:29`). Those suffixes repeat every 16 minutes 40 seconds and 100 seconds respectively. Front-desk IDs depend on local collection lengths and the millisecond component; separate clients can allocate identical IDs. Recollection uses truncated timestamps too. Firestore writes can overwrite unrelated records.
13. **Unsigned result entry starts with invented measured values.** `lab/frontend/widgets/result_entry_dialog.dart:47–75` prepopulates plausible patient results. Unsupported panels fall back to CBC parameters. Saving does not require actual measured values or validate the panel, values, units, or ranges.
14. **Only one report is supported per sample.** `central_data_store.dart:989` identifies an existing report by barcode alone. Entering results for another test on the same vial overwrites the previous panel.
15. **One signed report completes an entire order.** `central_data_store.dart:1090` marks the parent order complete without checking the remaining vials/tests/reports.
16. **Signer information is lost in persistence.** `data/models/report_model.dart:92` omits `pathologistName` from `toMap`, although `fromMap` reads it. The Firestore listener can replace a signed local report with one missing its signer.
17. **Clinical notes are discarded.** `saveTestResults` accepts `notes`, and `authorizeAndSignReport` accepts `clinicalInterpretation`, but neither persists them.
18. **Unknown samples can acquire fabricated patient records.** `saveTestResults` creates a sample with `PT-UNKNOWN` and a synthetic order ID if lookup fails. It does not create that order or initially persist that new sample, yet permits report creation and subsequent signing.
19. **Rack allocation does not enforce capacity or exclusivity.** `assignToRack` updates sample status before verifying the rack, permits overfilling, and does not remove a vial from its old rack. An unknown sample can also be added to a rack.
20. **Recollection loses essential workflow data.** `recordQcRejection` substitutes a generic home address, first test only, fixed branch and collector, and inserts an order directly without creating its advertised sample. Repeated rejection can create repeated recollections. Existing reports are not invalidated when a sample is rejected.
21. **Temperature validation contradicts the displayed requirement.** `phlebotomist_collection_request.dart:46` accepts 1–12°C while its error says 2–8°C. Non-finite numeric input is not rejected. Accession forcibly replaces temperature with 4°C (`central_data_store.dart:889`), concealing the recorded reading rather than capturing a new measurement.
22. **Custody attribution is often invented or incomplete.** The store uses hardcoded staff IDs/names, frequently omits `orderId` and `fromStatus`, and records a collection event while immediately setting the sample to `inTransit` without a matching transit event.
23. **Embedded audit events lose their IDs after a round trip.** `sample_event_model.dart:53` does not serialize `id`; embedded events are parsed without a document ID and receive `''`. `_syncSampleToFirestore` later uses those empty IDs as event document paths. This prevents reliable event persistence after reloading a sample.
24. **The audit trail is mutable.** `_syncSampleToFirestore` rewrites all existing event documents with merge semantics, uses client timestamps, and maintains a second embedded event list. Rules do not prohibit edits/deletes. Transaction-created events are not appended to the embedded list consumed by the central-store UI, so those views can disagree.

## High: persistence and synchronization

25. **Success does not mean data was saved.** The store returns after local mutation and launches unawaited Firestore writes. Errors are debug logs; the UI can announce successful booking, collection, or signature when persistence failed. When Firebase is unavailable, mutations have no durable fallback.
26. **Related records are written independently.** Orders, samples, reports, and events are not committed together. Partial failure or concurrent clients can leave contradictory records. Full sample/event-array replacement also risks losing concurrent updates.
27. **Demo records are always mixed with cloud records.** The central store seeds patients, orders, samples, reports, racks, and analyzers before loading Firestore. Empty cloud snapshots do not clear them. Production screens can display invented operational information and actions can write modified demo records to the configured project.
28. **Cloud deletions never remove local records.** `_subscribeToFirestoreCollections` only inserts or updates snapshot documents. Deleted orders, samples, and reports remain in memory until restart; seeded versions can reappear even then.
29. **Admin changes are separate, temporary state.** `admin/backend/services/admin_service.dart` maintains static in-memory lists instead of the central store/cloud. Branch creation, staff allocation/duty changes, and alert resolution do not persist or affect booking assignment. Dashboard TAT, rejection, and volume metrics are seeded constants rather than calculations from workflow events.
30. **Racks, QC logs, telemetry, and labels are not durably synchronized.** Store synchronization covers orders/samples/reports; rack updates and QC entries remain local. Front-desk print status/labels and collector sensor logs also remain local.
31. **All clients subscribe to all clinical documents.** Three unbounded collection listeners run before login, with no ownership filters, branch filters, pagination, or limits. This exposes data in memory and scales poorly in reads, memory use, and repeated provider refreshes. Listener subscriptions are not retained for cancellation on logout/disposal.
32. **Collector identity is hardcoded too.** `phlebotomist/frontend/providers/phlebotomist_provider.dart:30–35` refreshes `PH-204` after every store change. Other collectors see the wrong queue. Bookings always assign that collector, irrespective of branch or admin duty/allocation changes.
33. **Asynchronous refreshes can overwrite newer state.** Patient/lab/collector providers start full refreshes on every notification without cancellation or a request generation check. Several notifications occur during one mutation. Their asynchronous completions can race, and pending work can notify after provider disposal.

## Incomplete or misleading features

34. **The rendered barcode is decorative rather than a Code 128 encoding.** `frontdesk/frontend/widgets/barcode_widget.dart:66` generates arbitrary character-derived bar widths instead of the Code 128 symbol/checksum structure. It cannot serve as a reliable scanner-readable identity label.
35. **PDF download/printing is not implemented.** Patient and front-desk report actions show snackbars; they do not create/download a file or invoke a printer. `storage_service.dart` is a comment-only stub.
36. **Thermal printing is simulated.** `frontdesk/frontend/providers/frontdesk_provider.dart:128` waits on a timer, marks labels printed in memory, and reports printer success with no printer interaction or acknowledgment. Receipt printing is similarly simulated.
37. **GPS/telemetry claims do not match implementation.** `scan_vial_screen.dart:169` supplies fixed coordinates. Collection service discards latitude/longitude. Navigation shows a snackbar; temperature logs are local manual entries. Location and notification services are stubs; analyzer status is seeded rather than live hardware telemetry.
38. **Booking selections do not reflect the real network.** The screen's branch list differs from the admin list; the API always saves `branch-spoke-01` while using the selected display name. The booking date is fixed to tomorrow and has no picker. Slot availability, collector capacity, and valid future times are not checked.
39. **Validation is incomplete at service boundaries.** Patient booking validation checks only nonempty fields, allowing arbitrary patient IDs, prices, dates, and test names. Walk-in validation does not check gender even though label generation indexes `gender[0]`. Fasting verification is present in collection requests but not enforced. Client-supplied actor identities and amounts are trusted.
40. **Report readiness relies on substring matching.** `report_model.dart:88` treats any status containing `ready` or `verified` as ready, and ignores the constructor's `isReady` argument. Negated or unexpected imported statuses can therefore release reports incorrectly.
41. **Sample assignment and custody are conflated.** `sample_model.dart:74` aliases `assignedPhlebotomistId` to `currentCustodianId`. A handoff changes what appears to be the assigned collector, preventing stable assignment history.
42. **Tracking can display stale or unrelated data.** `track_sample_screen.dart` keeps a searched sample as a snapshot rather than reselecting it after store updates. A failed search falls back to the provider's active sample, leaving a different sample visible beneath a not-found message.

## Build, deployment, architecture, and tests

43. **Release signing is unreliable and permits debug keys.** Android release configuration falls back to a local debug keystore, but no keystore is tracked. Without a supplied key, the release signing configuration has no store file. Codemagic exports a relative `CM_KEYSTORE_PATH` within one script step; it is not reliably shared with later build steps, and Gradle resolves relative paths from the app project directory.
44. **Codemagic ignores analysis and test failures.** Both workflows append `|| true` to these commands. APK and Pages workflows are independent of the GitHub quality job, so passing quality gates are not a prerequisite to their builds/deployment. Formatting failures are explicitly ignored in the main CI job.
45. **Rules deployment is not wired up.** `firebase.json` contains Flutter app metadata but no Firestore rules deployment entry. The repository does not establish which rules are actually active remotely. Storage rules and database emulator/rules tests are absent.
46. **Authentication session restoration is missing.** The active auth provider starts with `_currentUser == null` and does not subscribe to Firebase auth-state changes or load the persisted current user. App identity and Firebase identity can disagree; page reload returns the app to the gateway.
47. **OTP completion handling is incomplete.** The provider returns a boolean immediately after awaiting `verifyPhoneNumber`, although callbacks can arrive later. Automatic verification supplies no callback from the provider. Web uses the same native phone-verification path without a separate web confirmation flow.
48. **Platform configuration is incomplete.** Firebase options return Android settings for every non-web platform; no iOS project is present despite iOS being a documented target. Android explicitly enables cleartext traffic, increasing the permitted transport surface unnecessarily.
49. **The repository contains parallel old/new implementations and stubs.** `lib/features/patient` has a separate mock provider/screens while `main.dart` uses `lib/patient/frontend`. Several other `features` files are compatibility exports or placeholders. Core error handling, validation, logging, route guards, and shared service abstractions are largely unimplemented. This makes the advertised architecture misleading and future edits easy to apply to unused code.
50. **Tests mostly validate the demo implementation.** Existing cross-role tests share one in-memory singleton and do not demonstrate separate-client synchronization, Firestore security, persistence round trips, failed writes, or concurrent barcode claims. Seed-user tests explicitly expect authentication without proving password verification. Missing coverage corresponds directly to the defects above.
51. **Build inputs are not fully reproducible.** Flutter SDK/container tags follow `stable`, and dependency declarations have no version constraints. The lockfile helps repeat package versions but does not pin the SDK or prevent broad upgrades. The README also links a missing LICENSE and describes stronger security, immutable custody, live telemetry, and completed downloads than the source implements.

## Suggested repair order

1. Isolate demo mode and remove authentication bypasses from real-data builds. Implement trusted role provisioning and restrictive, tested database rules.
2. Scope providers/queries to the authenticated identity and branch. Restore sessions and clear sensitive state on logout.
3. Consolidate writes into one validated, awaited transaction path; use collision-resistant IDs and atomic barcode ownership checks.
4. Correct report/panel modeling, signing authorization, serialization, audit-event IDs, QC/recollection, and completion rules.
5. Add durable persistence for admin/racks/QC/labels; replace simulated output and telemetry with real integrations or label those features clearly as demo-only.
6. Make release jobs enforce tests/analysis and test cloud behavior, authorization, concurrency, and serialization before deployment.
